# VideoCut — план реализации

## 1. Цель проекта

VideoCut — Telegram-бот с Telegram Mini App для быстрой обрезки видео.

Основной пользовательский сценарий:

```text
/start
→ приветственное сообщение
→ пользователь отправляет видео
→ бот создаёт временную сессию
→ пользователь открывает Mini App
→ выбирает начало и конец фрагмента
→ нажимает «Готово»
→ worker обрабатывает видео через FFmpeg
→ бот отправляет обрезанное видео в чат
→ исходник и результат удаляются
```

Видео не должно храниться постоянно. Файлы существуют только во временной директории на время одной операции и удаляются после отправки результата либо по TTL.

## 2. Архитектурное решение

```text
Telegram Bot
  ├── /start
  ├── приём video/document
  ├── скачивание во временный файл
  ├── создание session_id
  ├── кнопка открытия Mini App
  └── отправка результата

FastAPI
  ├── health check
  ├── проверка Telegram Web App initData
  ├── чтение временной сессии
  ├── потоковая отдача исходника в Mini App
  ├── валидация диапазона
  └── постановка задачи обработки

Redis
  ├── временные сессии
  ├── статусы задач
  ├── TTL
  └── очередь обработки

Worker
  ├── FFmpeg
  ├── точная обрезка
  ├── отправка результата через Bot API
  └── очистка временных файлов

Mini App
  ├── preview видео
  ├── timeline
  ├── выбор start/end
  ├── предпросмотр диапазона
  └── экран статуса
```

## 5. Предстоящие этапы реализации

### Этап 1. Стабилизировать контейнерный runtime

Задачи:

- использовать Fedora Podman через доступный API socket;
- не использовать локальный Docker daemon внутри Debian-контейнера;
- выбрать рабочую Compose-совместимую команду;
- проверить build всех образов;
- проверить запуск Redis, API и Mini App;
- добиться прохождения `GET /health`.

Проверка:

```bash
curl http://localhost:8000/health
```

Ожидаемый результат:

```json
{"status":"ok"}
```

Примечание: текущая сборка через legacy `docker-compose` ломается на схеме `http+docker`, а локальный `podman-compose` использует неправильный runtime внутри вложенного контейнера. Это инфраструктурное ограничение окружения, а не логики приложения.

### Этап 2. Добавить конфигурацию приложения

Задачи:

- общий `.env.example`;
- `BOT_TOKEN`;
- `REDIS_URL`;
- `MINI_APP_URL`;
- лимит размера файла;
- лимит длительности;
- TTL сессии;
- директория временных файлов;
- настройки FFmpeg.

Критерий:

- приложение стартует с валидной конфигурацией;
- отсутствующие обязательные настройки дают понятную ошибку;
- секреты не попадают в Git.

### Этап 3. Реализовать временные media-сессии

Сущность сессии в Redis:

```json
{
  "id": "random-session-id",
  "telegram_user_id": 123456789,
  "file_path": "/tmp/videocut/session/input.mp4",
  "status": "editing",
  "duration": 84.2,
  "width": 1920,
  "height": 1080,
  "created_at": "...",
  "expires_at": "..."
}
```

Статусы:

```text
created
uploaded
editing
processing
completed
failed
expired
```

Требования:

- криптографически случайный `session_id`;
- одна сессия связана с одним Telegram user ID;
- TTL в Redis;
- автоматическое удаление временной директории;
- одна активная сессия на пользователя в MVP.

### Этап 4. Реализовать приём видео ботом

Обработчики:

- `video`;
- `document` с MIME `video/*`.

Flow:

1. принять Telegram message;
2. проверить размер;
3. скачать файл во временную директорию;
4. проверить медиа через `ffprobe`;
5. сохранить метаданные в Redis;
6. отправить кнопку «Открыть редактор»;
7. передать в Mini App только одноразовый `session_id`.

Ошибки:

- неподдерживаемый тип файла;
- превышен размер;
- повреждённый файл;
- истекло место во временной директории.

### Этап 5. Реализовать авторизацию Mini App

Backend должен проверять Telegram `initData`.

Проверять:

- HMAC-подпись;
- дату авторизации;
- Telegram user ID;
- принадлежность сессии пользователю;
- срок действия сессии.

Нельзя доверять `user_id`, переданному только из frontend.

### Этап 6. Реализовать API сессий

Минимальный API:

```http
GET /api/sessions/{session_id}
GET /api/sessions/{session_id}/video
POST /api/sessions/{session_id}/trim
GET /api/sessions/{session_id}/status
```

`GET /api/sessions/{session_id}` возвращает metadata и статус.

`GET /api/sessions/{session_id}/video` отдаёт временный исходник потоково после авторизации.

`POST /api/sessions/{session_id}/trim` принимает:

```json
{
  "start": 8.5,
  "end": 42.0
}
```

Валидация:

```text
start >= 0
end > start
end <= duration
end - start <= max_output_duration
```

Повторный запрос при статусе `processing` не создаёт вторую задачу.

### Этап 7. Реализовать Mini App editor

Компоненты:

- video preview;
- timeline;
- левая ручка диапазона;
- правая ручка диапазона;
- time input;
- preview выбранного диапазона;
- кнопка «Готово»;
- состояние обработки;
- состояние ошибки;
- состояние истёкшей сессии.

Flow:

```text
открытие → GET session → загрузка video → выбор диапазона → POST trim → polling status
```

Опрос статуса — каждые 1–2 секунды.

### Этап 8. Реализовать очередь и FFmpeg worker

Worker получает:

```json
{
  "session_id": "session-id",
  "telegram_user_id": 123456789,
  "input_path": "/tmp/.../input.mp4",
  "start": 8.5,
  "end": 42.0
}
```

Для точной обрезки использовать FFmpeg с перекодированием:

```bash
ffmpeg \
  -ss 8.5 \
  -i input.mp4 \
  -t 33.5 \
  -map 0:v:0 \
  -map 0:a? \
  -c:v libx264 \
  -c:a aac \
  -movflags +faststart \
  output.mp4
```

Worker обязан:

1. проверить входной файл;
2. собрать аргументы FFmpeg только из валидированных параметров;
3. запустить обработку;
4. проверить exit code;
5. проверить выходной файл;
6. отправить результат через Bot API;
7. обновить статус;
8. удалить input;
9. удалить output;
10. инвалидировать Redis-сессию.

### Этап 9. Добавить cleanup и отказоустойчивость

- повторное нажатие «Готово»;

## 8. Расширенная спецификация будущего функционала

Этот раздел описывает не только технические задачи, но и ожидаемое поведение продукта, UX-правила и приоритеты развития. Сначала реализуется короткий и надёжный сценарий обрезки, затем на его основе добавляются дополнительные операции.

### 8.1. Принципы продукта

VideoCut должен ощущаться как «быстрый инструмент внутри Telegram», а не как тяжёлый видеоредактор.

Основные принципы:

1. **Минимум действий.** Пользователь не должен разбираться в форматах, кодеках и FFmpeg.
2. **Предсказуемый результат.** До запуска обработки понятно, какой фрагмент будет оставлен и сколько он длится.
3. **Mobile-first.** Основной интерфейс проектируется для большого пальца и маленького экрана.
4. **Без постоянного хранения.** Исходник и результат живут только в рамках временной сессии.
5. **Никаких скрытых операций.** Пользователь видит загрузку, обработку, ошибку и завершение.
6. **Безопасность по умолчанию.** Session ID не заменяет авторизацию, а только идентифицирует временную сессию.
7. **Постепенное усложнение.** Новые функции не должны перегружать основной экран.

### 8.2. Сценарии бота

#### `/start`

Первое сообщение должно коротко объяснять ценность:

```text
Привет! Отправь видео — выбери нужный фрагмент — получи готовый файл обратно сюда.
```

Кнопки первого экрана:

- `Отправить видео` — подсказка пользователю, если Telegram позволяет открыть выбор файла;
- `Как это работает` — короткая инструкция из трёх шагов;
- `Настройки` — позже, после появления пользовательских настроек.

Повторный `/start` не должен создавать сессию и не должен сбрасывать активную обработку.

#### Приём видео

Бот принимает:

- Telegram `video`;
- Telegram `document` с видео MIME type;
- в будущем — видео, отправленное как файл с неизвестным MIME, если `ffprobe` подтверждает видеопоток.

После получения бот показывает промежуточный статус:

```text
Проверяю видео…
```

После успешной проверки:

```text
Видео готово. Открой редактор и выбери нужный фрагмент.
```

Кнопка должна быть Telegram Web App-кнопкой и содержать только временный идентификатор сессии.

#### Повторная отправка

Если у пользователя уже есть активная сессия:

- не удалять её молча;
- спросить, заменить ли текущее видео;
- старую сессию удалить только после подтверждения или по TTL.

Если обработка уже идёт, новое видео должно либо попасть в очередь, либо получить понятное сообщение о текущем лимите. В MVP разрешается одна активная сессия.

### 8.3. Экран Mini App

#### Состояния экрана

Mini App должен иметь отдельные состояния:

1. `loading` — проверка initData и загрузка метаданных;
2. `ready` — видео загружено, можно редактировать;
3. `video-error` — видео не удалось загрузить;
4. `invalid-session` — сессия чужая, истекла или уже использована;
5. `submitting` — запрос на обработку отправляется;
6. `processing` — worker обрабатывает файл;
7. `completed` — результат отправлен ботом;
8. `failed` — обработка завершилась ошибкой.

Для каждого состояния нужен понятный текст и действие восстановления. Нельзя оставлять пользователя на бесконечном spinner.

#### Верхняя панель

В верхней панели:

- название операции: `Обрезка видео`;
- кнопка закрытия Mini App;
- при необходимости — индикатор несохранённых изменений.

При закрытии во время редактирования сессия не удаляется сразу: она остаётся доступной до TTL.

#### Preview

Preview должен:

- поддерживать обычное воспроизведение;
- показывать текущую позицию;
- перематываться в начало выбранного диапазона;
- отображать play/pause крупной кнопкой;
- корректно работать без аудиодорожки;
- не загружать отдельную копию файла в браузер целиком, если это можно избежать потоковой отдачей.

После изменения начала или конца диапазона preview должен сохранять предсказуемое поведение: кнопка предпросмотра запускает именно выбранный фрагмент.

#### Timeline

Timeline включает:

- thumbnail-кадры или нейтральную шкалу, если генерация кадров ещё не реализована;
- левую ручку `start`;
- правую ручку `end`;
- текущий playhead;
- подписи времени;
- визуально выделенный оставляемый диапазон.

Требования к управлению:

- ручки не могут пересечься;
- минимальная длина результата задаётся конфигурацией;
- время округляется до разумной точности интерфейса;
- для точной обрезки можно вводить миллисекунды, например `00:12.500`;
- drag должен работать мышью, touch и клавиатурой;
- при перемещении ручки timeline не должен скроллить всю страницу.

#### Точное редактирование

Под timeline показываются поля:

```text
Начало   00:08.500
Конец    00:42.000
Длина    00:33.500
```

Дополнительные действия:

- `-1 сек`;
- `+1 сек`;
- `-0.1 сек`;
- `+0.1 сек`;
- переход к текущей позиции видео.

Если введено некорректное значение, поле не должно отправлять запрос на backend. Ошибка показывается рядом с конкретным полем.

#### Кнопка завершения

Основная кнопка называется `Готово` или `Обрезать видео`.

Перед отправкой можно показывать компактное подтверждение:

```text
Оставить фрагмент 00:08.500 — 00:42.000?
Длительность результата: 00:33.500
```

Во время отправки кнопку нужно заблокировать, чтобы исключить дублирование задач.

### 8.4. UX-фишки первой и последующих версий

#### Фишки MVP

- открытие редактора сразу после получения видео;
- сохранение диапазона при повторном открытии Mini App;
- отображение длительности, разрешения и размера файла;
- понятные ошибки без технических traceback;
- статус обработки в Mini App;
- автоматическая отправка результата в текущий чат;
- удаление всех временных файлов;
- корректная работа с видео без аудио.

#### Фишки версии 1.1

- thumbnail-strip с кадрами по timeline;
- пресеты `Первые 5 секунд`, `Последние 5 секунд`, `Первые 30 секунд`;
- `Выбрать весь ролик`;
- быстрый переход к началу и концу;
- кнопка `Оставить наоборот` для удаления выбранного фрагмента;
- возможность начать новое редактирование после завершения;
- компактный прогресс обработки;
- повторить обработку после временной ошибки.

#### Фишки версии 1.2

- mute/remove audio;
- извлечение аудио;
- экспорт в GIF для коротких фрагментов;
- изменение скорости: `0.5x`, `1x`, `1.5x`, `2x`;
- поворот видео;
- базовое кадрирование под `9:16`, `1:1`, `16:9`;
- сжатие с выбором качества;
- конвертация контейнера MP4/MOV/WebM;
- отображение примерного размера результата.

#### Расширенный редактор

Только после стабилизации базовых операций:

- несколько фрагментов на одном timeline;
- изменение порядка фрагментов;
- склейка выбранных фрагментов;
- простые переходы;
- обложка результата;
- текст и watermark;
- субтитры;
- шаблоны для Reels, Shorts и Stories.

Сложный многодорожечный редактор не входит в MVP: он резко увеличивает объём frontend-логики, число ошибок и требования к preview.

### 8.5. Операции обработки и их параметры

Backend должен иметь единый формат задания:

```json
{
  "operation": "trim",
  "session_id": "...",
  "parameters": {
    "start": 8.5,
    "end": 42.0,
    "audio": "keep",
    "quality": "source"
  }
}
```

Операции:

- `trim` — оставить один диапазон;
- `cut` — удалить диапазон;
- `mute` — удалить аудиодорожку;
- `extract_audio` — сохранить только аудио;
- `gif` — экспортировать короткий диапазон в GIF;
- `speed` — изменить скорость;
- `resize` — изменить разрешение или aspect ratio;
- `convert` — сменить контейнер и кодеки.

Каждая операция должна иметь:

- отдельную схему параметров;
- серверную валидацию;
- лимиты по длительности и размеру;
- оценку ресурсоёмкости;
- тесты успешного и неуспешного сценария.

Пользовательские значения не должны напрямую превращаться в shell-команду. Команда FFmpeg собирается из белого списка параметров.

### 8.6. Сессии, временные файлы и жизненный цикл

Для каждой сессии создаётся отдельная директория:

```text
/tmp/videocut/{session_id}/
├── input
├── thumbnails
├── output
└── metadata.json
```

`session_id` не должен быть последовательным. Рекомендуется UUID4 или токен, созданный криптографически безопасным генератором.

Жизненный цикл:

```text
created
→ downloading
→ uploaded
→ editing
→ queued
→ processing
→ sending
→ completed
→ deleted
```

Ошибочные переходы:

```text
любое состояние → failed
любое неактивное состояние после TTL → expired
```

Для каждой сессии хранить только необходимое:

- Telegram user ID;
- Telegram chat ID;
- исходный путь;
- MIME type;
- размер;
- длительность;
- разрешение;
- FPS;
- статус;
- timestamps;
- параметры текущей операции.

Не хранить содержимое видео в Redis или PostgreSQL.

### 8.7. Очередь обработки

Очередь нужна, чтобы скачивание и FFmpeg не блокировали Telegram polling или HTTP API.

Правила очереди:

- задача получает уникальный job ID;
- повторная отправка того же запроса не создаёт дубликат;
- статус задачи доступен через API;
- задача имеет timeout;
- после падения worker задача либо повторяется ограниченное число раз, либо становится `failed`;
- пользователь не должен видеть внутреннюю структуру очереди.

В MVP можно использовать Redis Lists или Streams. При росте нагрузки очередь можно заменить на отдельный брокер, не меняя API Mini App.

Прогресс:

- `queued` — задача ожидает worker;
- `processing` — FFmpeg работает;
- `sending` — результат передаётся Telegram;
- `completed` — Telegram подтвердил отправку.

Если FFmpeg не позволяет надёжно получить процент, показывать этапы вместо фальшивого процента.

### 8.8. Работа с FFmpeg

Для операций требуется:

- `ffprobe` для чтения metadata;
- таймаут процесса;
- ограничение размера результата;
- ограничение CPU и памяти контейнера worker;
- безопасные временные имена;
- проверка выходного файла после завершения.

Режимы обрезки:

1. **Точный режим.** Перекодирование, корректно работает на произвольной временной позиции.
2. **Быстрый режим.** Stream copy, быстрее, но начало зависит от keyframe.

В интерфейсе быстрый режим можно добавить только после того, как точный режим будет стабилен. По умолчанию используется точный режим.

Результат проверяется по следующим признакам:

- файл существует;
- размер больше нуля;
- `ffprobe` видит видеопоток;
- длительность находится в допустимом диапазоне;
- размер не превышает Telegram-лимит;
- при наличии аудио аудиопоток читается корректно.

### 8.9. Авторизация и безопасность

Для каждого API-запроса Mini App:

1. frontend отправляет Telegram `initData`;
2. backend проверяет подпись по bot token;
3. backend извлекает Telegram user ID;
4. backend сравнивает его с владельцем сессии;
5. backend проверяет TTL и статус.

Защита от атак:

- нельзя принимать произвольный путь к файлу от frontend;
- нельзя передавать shell-фрагменты в параметрах операции;
- нельзя выдавать session metadata без авторизации;
- нельзя делать session ID предсказуемым;
- ограничить частоту API-запросов;
- ограничить число активных задач;
- ограничить размер тела HTTP-запроса;
- не логировать bot token, initData и персональные данные целиком;
- не оставлять видео в логах, cache или build context.

### 8.10. Ошибки и сообщения пользователю

Внутренняя ошибка и пользовательское сообщение разделены.

Примеры:

| Ситуация | Сообщение пользователю |
|---|---|
| Файл слишком большой | `Файл слишком большой. Отправь видео меньшего размера.` |
| Видео не читается | `Не удалось прочитать видео. Попробуй другой файл.` |
| Сессия истекла | `Сессия истекла. Отправь видео заново.` |
| Некорректный диапазон | `Проверь начало и конец фрагмента.` |
| Очередь занята | `Видео принято и ждёт обработки.` |
| FFmpeg завершился с ошибкой | `Не удалось обработать видео. Попробуй ещё раз.` |
| Telegram не принял файл | `Результат готов, но Telegram не смог его отправить.` |

В логах при этом сохраняются job ID, session ID, тип ошибки и техническая причина без содержимого файла.

### 8.11. Лимиты и политика ресурсов

MVP:

```text
Максимальный размер входа: 500 МБ или фактический лимит Telegram
Максимальная длительность: 15 минут
Максимальная длина результата: 15 минут
Одна активная сессия на пользователя
Одна активная задача на пользователя
TTL сессии: 30 минут
TTL зависшей задачи: 60 минут
```

Лимиты должны быть конфигурацией, а не захардкоженными значениями.

При нехватке диска новые загрузки временно блокируются с понятным сообщением. Cleanup не должен ждать перезапуска контейнера.

### 8.12. Наблюдаемость и эксплуатация

Добавить:

- JSON или структурированные логи;
- correlation ID для запроса, session ID и job ID;
- `/health` для процесса;
- `/ready` для Redis и доступности временной директории;
- метрики количества загрузок, ошибок и времени обработки;
- измерение размера временной директории;
- логирование переходов статуса;
- предупреждение при приближении к лимиту диска.

Необходимые алерты:

- Redis недоступен;
- worker не обрабатывает задачи;
- резко выросло число FFmpeg ошибок;
- заканчивается диск;
- Telegram API недоступен;
- увеличилось среднее время обработки.

### 8.13. Монетизация и ограничения после MVP

Монетизацию не включать до проверки основного сценария, но архитектура должна позволять добавить:

- дневной лимит бесплатных обработок;
- лимит длительности для бесплатного пользователя;
- платную точную обрезку или высокое качество;
- приоритетную очередь;
- отсутствие рекламных сообщений;
- оплату через Telegram Payments.

Лимиты должны храниться отдельно от media-сессии. Временная сессия не является аккаунтом или историей пользователя.

## 9. Definition of Done для MVP

MVP готов, когда:

- `/start` отвечает приветствием;
- бот принимает video и video-document;
- бот создаёт временную сессию;
- пользователь открывает Mini App;
- Mini App показывает его видео;
- пользователь выбирает начало и конец;
- чужая сессия недоступна;
- `Готово` запускает одну задачу обработки;
- worker обрезает видео через FFmpeg;
- бот отправляет результат в чат;
- исходник и результат удаляются;
- ошибки понятны пользователю;
- истёкшие сессии очищаются;
- автоматические тесты проходят;
- весь сценарий запускается в контейнерах через Podman.
